## Dependencies

This project uses [uv](https://docs.astral.sh/uv/) for fast, reliable Python package management.

**Installing dependencies locally:**
```bash
uv sync              # Install all dependencies
uv sync --dev       # Include dev dependencies
```

**Managing dependencies:**
- Edit `pyproject.toml` to add or update dependencies
- Run `uv lock` to generate `uv.lock` (includes wheels for macOS and Linux)
- Commit both `pyproject.toml` and `uv.lock` to version control

**Generating `uv.lock` via Docker:**

If you don't have `uv` installed locally, generate the lock file using Docker:

```bash
docker run --rm -v "$(pwd):/code" -w /code ghcr.io/astral-sh/uv:python{{ cookiecutter.python_version }}-bookworm-slim uv lock
```

This mounts your current directory and runs `uv lock` inside the container, writing the `uv.lock` file to your project.

The `uv.lock` file is **platform-aware** (includes wheels for macOS-aarch64, linux-aarch64, and linux-x86_64), ensuring reproducible installs locally and in Docker. macOS x86_64 is excluded because `torch==2.5.1` has no wheel for it.

## CLI

The project exposes a small command-line interface implemented in `src/{{ cookiecutter.project_name }}/cli.py` using Typer. The following commands are available:

- `data`: Preprocess raw data into the processed data directory. Example: `proj data`.
- `train`: Train a model from processed features and labels and save the trained model. Example: `proj train`.
- `test`: Run the test suite using `pytest` (runs `pytest tests/`). Example: `proj test`.
- `format`: Format the source code using `ruff format`. Example: `proj format`.
- `eval`: Evaluate a trained model on test features and write predictions. Example: `proj eval`.
- `plots`: Generate plots from processed data and save to the figures directory. Example: `proj plots`.
- `run-pipeline`: Run all stages in order (`data` → `train` → `eval` → `plots`), stopping at the first failure. Use `--from` / `--to` to run a contiguous slice, e.g. `uv run cli run-pipeline --from train --to eval`. Every selected stage reruns (no caching){% if cookiecutter.use_dvc == 'yes' %}; use `dvc repro` for that{% endif %}. After each stage the files it declares in `pipeline.py` must exist, otherwise the run fails.

The stage order and each stage's outputs live in `STAGES` in `src/{{ cookiecutter.project_name }}/pipeline.py`. Artefact paths are defined once in `config.py`.

Each command accepts parameters (paths) and defaults to project directories defined in `src/{{ cookiecutter.project_name }}/config.py`.

Invoke the CLI through your package entrypoint or via Python. For example, if your package is installed or available in the current environment you can run:

```
uv run {{ cookiecutter.project_name }}.cli <command>
```

{% if cookiecutter.use_dvc == 'yes' %}## Cached pipeline with DVC

`dvc.yaml` declares the same four stages for cached execution. `dvc repro` reruns only stages whose dependencies, parameters or outputs changed, and `dvc.lock` records exactly what produced the current artefacts.

First-time setup (DVC needs a git repository):

```bash
git init                      # if not done already
uv sync                       # installs dvc
dvc add data/raw              # version the raw data; commit the generated data/raw.dvc
dvc remote add -d storage s3://<bucket>/<path>   # see the comments in .dvc/config (S3-compatible stores need `uv add "dvc[s3]"`)
dvc repro                     # run the pipeline; commit dvc.lock
dvc push                      # upload data and models to the remote
```

Day to day: `dvc repro` (run what changed), `dvc params diff` (what changed in hyperparameters), `dvc pull` (fetch data and models for the current commit).

Things to know:
- `deps` in `dvc.yaml` are listed by hand. DVC does not trace imports, so when a stage starts importing another module, add that module to the stage's `deps`, otherwise editing it will not rerun the stage.
- `data/`, `models/model.pkl` and `reports/` are intentionally not in `.gitignore`: DVC writes the right ignore entries itself and refuses paths that git already ignores.
- Caching assumes a stage is a deterministic function of its declared inputs. Stages that depend on unseeded randomness, wall-clock time or external services should list the seed in `params.yaml`, or be marked `always_changed: true`.
- `tests/test_dvc.py` checks that `dvc.yaml` matches `STAGES` in `pipeline.py` (names, order, commands, outputs). Update both when you add a stage.
